0. この文書の目的
------------------

この文書は、現在のTobkiriを次の設計へ全面移行するための、実装可能な粒度の計画である。

  Packが機能を持つ。
  Contractが意味を定義する。
  Requestが依頼を表す。
  Runtimeが解決・隔離・配送する。
  Policyが境界を越える作用を制御する。
  Profileが実行環境を構成する。

最終目的は、正確なcontent digestを過去に有効化したことがない未知のPackでも、既知のContractに適合し、必要な隔離・Policy・Grant・監査が成立する場合だけ安全に接続できる実行環境を作ることである。

本計画のnormative inputは、このリポジトリへcommitされた本計画、ADR、schema、
canonical vector、生成可能なinventoryとする。ダウンロード済みの
「Tobkiri Pack Architecture v1.1 bundle」と3件の読み取り専用subagent調査は
設計作業時のinformative inputであり、privateな調査結果または入手不能なbundleを
仕様の根拠として要求しない。bundleの照合用SHA-256は次のとおり。

  507b8c42044c9931a3d10ab5fefbc31eb397f2093ce82f4c01f75a86acb07834

注意:

  - v1.1のメモリ・ディスク・起動時間はengineering estimateであり実測値ではない。
  - 設計開始時は既存Packの後方互換や重要stateの保持を必須にしない前提だった。
    実装済みcutoverでは既存Packをv4 artifactへ移行し、旧production経路を
    到達不能にしたうえで、必要なユーザーstateを明示migration境界で扱う。
  - 実装開始前に、repo commit、対象tree、入力ファイルpath/digest、scanner versionを
    持つtracked inventory JSONを生成し、CIで再生成差分を検査する。
  - bundleを将来normative inputへ昇格する場合は、本体または不変URI、byte size、
    media type、構成ファイルhash、元commitをrepository管理する。


1. 今回確定する設計判断
----------------------

1.1 Functionは消滅させず、公開境界だけOperationへ置換する

  - UI上の「Function」という呼称は残してよい。
  - Pack内部のPython/Rust/JS関数は実装詳細として自由に使える。
  - Pack間公開APIはContract Operationだけにする。
  - 他Packはmodule名、file path、symbol名、FunctionRegistry IDを指定できない。
  - legacy FunctionRegistryは最終的に削除する。
  - Workflow stepもFunction名ではなくcontract_id + operation_idを指定する。

1.2 importの扱い

  - 同一PackArtifact内で、Packに同梱されたmoduleをimportすることは自由。
  - 同じ専用sandbox/PackVM内の内部module importにPolicy承認は不要。
  - ecosystem PackをHost processへimportすることは禁止する。
  - cross-Pack importも禁止する。
  - host importは「Policyで許可可能な権限」ではない。許可すると隔離境界そのものが消えるためである。
  - TCBだけがHost in-processで動ける。TCBをPack扱いしない。

1.3 Sandbox authorityとHost authorityの根本境界

Runtimeが直接定義する根本authorityは二つだけとする。

Sandbox authority:

  - Pack専用sandbox内の同梱code import、純粋計算、内部Function
  - Pack専用tmp/private state
  - sandbox内部だけの子process、内部IPC
  - 原則としてユーザーApproval不要
  - CPU、RAM、deadline、disk、process/thread、output、concurrency等のresource limitはHostが常時強制
  - raw network、Host filesystem、他Pack state、Host process、credential、OS、deviceへ到達不能

Host authority:

  - sandbox外のHost resourceまたは外部作用へ到達できる能力
  - exact Host Capability Provider Function/Operationだけが実装可能
  - Provider trust、caller-specific Grant、ExecutionDomain enforcement、InvocationLease、authoritative auditが必要
  - 通常Packのmanifest、publisher署名、Profile activationだけでは取得・昇格不能

別PackへのContract Requestは常にRuntime routing、schema、identity検査を通るが、それ自体をHost authorityとはしない。RequestがHost effect、shared authoritative resource、sensitive data disclosureを要求する場合だけ、対応するGrant/Policyを追加評価する。

Runtime immutable safety policyは、この根本境界、identity、isolation、Grant、Lease、audit、revocation、resource limitだけを非上書き可能な下限として強制する。filesystem、Slack、camera、printer等の全permission taxonomyやvendor semanticsをCoreへ中央実装しない。

1.4 Host CapabilityをFunction/Operationとして拡張する

sandbox外の具体的能力は、Host Extension PackまたはRuntime TCBが提供するHost Capability Provider Functionとして登録する。

  - filesystem、HTTP、credential付きAPI、process、camera、USB、clipboard、print等をFunction/Operationとして追加可能
  - Host Extension SDKがnamespaced Capability Provider registrationを提供
  - operation schema、scope schema、attenuation、risk、Approval metadata、audit metadata、Provider ceilingを署名済みdeclarationとして登録
  - 任意Policy code、identity resolver、Grant matcher、Approval rendererをKernelへin-process loadしない
  - normalize/subset/intersectionは安全なdeclarative DSL、Host-owned Broker/Handle、capability-restricted Wasm、または明示TCB Host Extension processで強制
  - semanticsをHostが安全に比較できなければexact-request one-shotまたはopaque trusted-host scopeへ落とし、細粒度永続Grantを装わない

trust classはNormal Sandbox Pack、Host Extension Pack、Runtime TCBの3つとする。Capability ProviderはFunction roleであり、roleだけではauthorityを得ない。Normal Packはmanifest変更やProfile設定によってHost Extensionへ昇格できない。

署名、authority、enforcementを三層へ分離する。

  PackArtifact identity:
    publisher、署名、配布、更新、parent artifact digest、Function subartifact digest inventory。
    Pack trustはPack内全FunctionへのHost authorityではない。

  FunctionPrincipal:
    exact parent artifact digest + Function implementation/subartifact digest
    + Function ID + Contract revision digest + Operation ID。
    ProviderAuthorityRecord、Approval、Grant、Effect scopeのauthority単位。

  ExecutionDomain:
    process/Wasm Component instance/sandbox + Host-assigned domain ID
    + authenticated IPC channel + process/component identity + boot epoch
    + OS sandbox/entitlement + ResourceHandle namespace。
    Function ID自己申告ではなくHost spawn/routing/channelからprincipalを固定。

Host authorityの行使方式は二つとする。

  lease_only:
    raw Host authorityはHost Kernel/Brokerが保持し、Providerへはrequest-bound
    InvocationLease、opaque ResourceHandle、sealed CredentialLease、限定importだけを渡す。

  os_entitlement:
    OSがextension processへ直接権限を付与する必要がある能力。
    exact dedicated processをauthority-bearing TCBとして扱い、least privilege、
    blast radius表示、egress制限、watchdog、background default deny、revoke時killを必須にする。

ApprovalRecord、ProviderAuthorityRecord、GrantRecord、InvocationLeaseを分離する。

  ApprovalRecord:
    ユーザー/管理者がimmutable snapshotを見て行った意思決定記録。runtime authorityではない。

  ProviderAuthorityRecord:
    exact Provider FunctionPrincipal/ExecutionDomainが実装できる最大Host authority ceiling。
    caller利用権限ではない。

  GrantRecord:
    exact caller FunctionPrincipalがspecific Profileでexact target Provider FunctionPrincipalを
    normalized scope内で利用できる保存authority。Host authority DBだけが発行・保存する。

  InvocationLease:
    exact caller/target FunctionPrincipal、ExecutionDomain、domain boot epoch、
    Request/effect digest、ResourceHandle namespaceへbindしたsingle-use/non-transferable token。

ユーザーUIではProvider trust/審査とcaller-to-Provider Use Approvalを一つのtransactional approvalへまとめてよい。内部recordは分離し、全recordをatomic commitできない場合はauthorityを残さない。matching ProviderAuthorityが既にあればUse Approvalだけを表示し、Grant scope内の反復利用では再promptせずRequestごとにLeaseだけ再発行する。

ProfileはPack/Provider/Function routing、requested caller edge/scope、authority DB内Grantへのopaque reference、ProfileAuthoritySnapshot digestだけを持つ。Profile file、Pack state、通常user configはauthorityをmint、拡張、署名、exportできない。

正規化済みRequest scope Rは、次のすべての範囲内である場合だけ実行できる。

  R subset-of caller Function/Operation Effect ceiling
  R subset-of Runtime immutable safety policy
  R subset-of Profile/admin ceiling
  R subset-of caller-specific Use Grant
  R subset-of ProviderAuthority ceiling
  R enforceable-by selected ExecutionDomain/OS mode

identity/snapshot/domain/revocation binding不一致、unknown/unverifiable semantics、audit/use reservation失敗はdenyする。Approvalはintersectionへ含めず、authority発行のprovenanceとする。

すべてのauthority recordはexact parent artifact digestとFunction implementation digestへbindする。version label単独はidentity/失効根拠にしない。対象Function digest、publisher lineage、authority semantics、ExecutionDomain securityが同じか非拡張で、UpdateTrustPolicyが許可する場合だけ新parent digest向けsuccessor recordを発行する。旧recordを新artifactへ直接一致させない。

Host authority仕様は docs/ADR-014_BOUNDARY_CAPABILITY_GRANTS.txt、非Function側の
security lifecycleは docs/ADR-015_RUNTIME_SECURITY_LIFECYCLE.txt を正本とする。

1.5 ExecutionDomain共有とco-location invariant

Packが同じであることはauthority domain共有理由にならない。

  - 異なるProvider ceiling、Effect scope、OS entitlement、ResourceHandle class、credential access、background policy、trust、revocation lifecycleを持つFunctionPrincipalを同一native address spaceへ同居させない。
  - 承認済みProvider Functionと未承認Functionはraw FD、Handle、Lease、credential、writable memory、environment secret、authenticated capability channelを共有しない。
  - caller-specific Host Grantを持つNormal Functionも、Function identityをHostが強制できるWasm instance/worker/domainへ置く。同じprocessのFunction ID自己申告だけでcallerを区別しない。
  - dedicated OS process、per-Function/Operation Wasm Component instance、Host-owned Brokerに対するunprivileged worker、verified authority-equivalence domainを認める。
  - authority-equivalence domainへ同居できるのは、同一ceiling/scope class/trust/lifecycleで相互co-locationが明示承認されたprincipalだけ。
  - 一つのFunctionが異なるauthorityの複数Operationを持つ場合、Operation別domainまたはper-invocation capability importで分離する。
  - 通常の権限を持たない同一Pack内部helperは専用PackVM内で共有してよい。
  - shared mutable stateはStorage Contract経由とし、domain外のambient共有を作らない。
  - replicaは同一FunctionPrincipal/authority classの別ExecutionDomainとして扱う。

1.6 Profile有効化とVM起動を分離する

Profileに100 Packが存在しても100 VMを起動しない。

  Artifact: Absent -> Staged -> Verified -> Installed -> Resolved
  Logical:  Resolved -> ProfileMember -> LogicallyActive -> Prepared -> Dormant
  Physical: Dormant -> AdmissionPending -> Starting -> Evidencing -> Ready
            -> Busy <-> Idle -> Stopping -> Stopped

on_demand/event_wake PackはDormantのままProfile commit可能とする。eager/continuousだけをactivation時のreadiness gateにする。

1.7 Distribution、Bundle、Suite

  - Packは署名、version、state、Provider ownershipの行政単位。
  - Distributionは複数Packの推薦、pin、取得元、互換組合せを記述する署名付き文書。
  - DistributionはPackではなく、権限も実行コードも持たない。
  - Bundle/Suiteというユーザー向け配布名は使用してよいが、内部ではDistribution manifestへ正規化する。
  - 一括installはできるが、一括approval、一括Grant、共有sandbox、共有stateを意味しない。
  - 現在のPack kind="bundle"は実行意味を持たせず、v4では削除するかdistribution artifactへ移す。

1.8 OSとライトユーザー向け要件

  - Docker、Homebrew、手動shell commandを利用条件にしない。
  - production backendはアプリに同梱し、guided installerがOS consent、optional feature、reboot resumeを扱う。
  - macOS: direct Virtualization.framework supervisor。
  - Windows: WHPX-backed PackVM supervisor。PackごとのWSL distroは使わない。
  - Linux: Firecracker/KVM + jailer-equivalent hardening。
  - certified backendが使えなければunknown native/Python Packをactivation拒否する。
  - process-only、shared Lima/WSL、Docker、host executionへ弱くfallbackしない。
  - Wasm-compatible PackはWasmtime Component/WASIのL3を優先する。

1.9 Base Pack、Shell Pack、Application Pack

Base Packとpresentation technologyを直交させる。

  - Base PackはProfileの機能構成rootであり、capability graph、default routing、
    state owner、backend Provider、Tool/Workflow catalog、Shell要件を定義する。
  - Base PackはTauri/Electron/CLI runtimeまたはHost authorityを暗黙に含まない。
  - Shell Packはapp.shell.v1を実装し、ユーザー入出力とpresentation lifecycleを持つ。
  - setup UIはBase Packを選択した後、compatibleなShell Providerを選択する。
  - ProfileLockはexact Base Pack、Shell Pack、binding、ArtifactVariantをpinする。

標準候補:

  defaults-basepack
    + shell.tauri.default
    + shell.electron.default
    + shell.cli.default

Profileへ単なるtype=tauri/cli/electronを書いてRuntime Coreを分岐させない。
内部ではexact app.shell.v1 Providerを解決する。experience role、presentation kind、
technology、ExecutionDomainを別軸にする。

  experience role:
    shell、frontend_contribution、standalone_app、cli、headless

  presentation kind:
    declarative、isolated_web、packaged_process、terminal_stdio、remote_ui

  technology metadata:
    tauri、electron、native、web等。trust/authority classではない。

CLI Shell選択時はcli.command/prompt/renderer/completion Contributionだけを解決し、
GUI route/WebView/window artifactをmaterializeしない。Tauri/Electron Shellは
graphical UI Contributionだけを解決する。同じPackがbackend ProviderとGUI/CLI両方の
Contributionを提供してよいが、Shell非選択側は起動しない。Shell変更だけでbackend
Provider identity、state owner、Host Grantを変更しない。

Tauri integrationは三役へ分ける。

  shell.tauri.*:
    prebuilt Tauri Shell。app.shell.v1とisolated/declarative UI hostを提供。

  runtime.tauri.application.*:
    完成済みstandalone Tauri artifactの検証、起動、停止、観測を提供。

  dev.tauri.toolchain.*:
    cargo tauri dev、npm run dev、build、bundle等をDevelopment Realmだけで提供。

production activationでcargo tauri dev、npm run dev、package install、source buildを
実行しない。macOS .app、Windows bundle、Linux package等の完成済み署名variantを
ProfileLockへpinする。Electronも同じ分離とし、framework overheadをresource会計する。

standalone Application Packはfrontend、native backend、sidecar、Contract、
ExecutionDomain、OS別ArtifactVariantを明示する。Tauri内部frontend/native commandは
application内部通信にできるが、Pack間公開処理はContract、Host effectはADR-014を通す。
任意PackのRust command/pluginをHost Tauri launcherまたは別Shellへlinkしない。

現行desktop_app.commandは任意Host process起動にすぎず、Tauri対応を意味しない。
v4 migration時にShell、standalone Application、CLI Contribution、backend Provider、
Development toolchainへ分類し、productionではarbitrary command-string launchを削除する。

正式仕様は docs/ADR-016_BASE_SHELL_APPLICATION_MODEL.txt を正本とする。


2. 現在ブランチの具体的な状態
------------------------------

2.1 既に存在する資産

現在はゼロからではない。少なくとも次が実装済みであり、考え方またはテスト資産を再利用できる。

  - strictなPack v3 JSON Schema
  - PackArtifactのhash、extra file、symlink、tamper検査
  - Ed25519署名、publisher/key ID/revocation、trust store
  - ContractDescriptor、ContractRequirement、ProviderDescriptor
  - semver、priority、one/keyed/chain等のdeterministic resolution
  - ResolvedProfileとstale detectionの一部
  - Python/TypeScript/Dartのgenerated contract型とdrift test
  - Command Protocol v1と55 commandのcatalog/invoke/events/approval系
  - process provider用bounded process runner
  - timeout時process-tree cleanupに使えるcancel_event実装
  - managed sandbox manager、template、policy、state store、auditの土台
  - macOS Lima、Windows WSL2、Linux Bubblewrap/systemd cgroup経路
  - Tool brokerのresolve -> validate -> guard -> policy -> authorize -> execute -> normalize -> audit骨格
  - connector inboundの署名検証とreplay ledger
  - approval/authority service、Grant manager、secret encryption
  - archive traversal/zip bomb対策付きPack staging
  - GUI contribution、scheduler、workflowの部分実装と画面試作

2.2 数量ベースの現状

確認コミット時点で、ecosystem配下には次がある。

  - ecosystem.json: 141個
  - rumi.pack.v3.json: 95個
  - v3 provided contracts: 158件
  - v3 required contracts: 166件
  - v3 entrypoints: 158件
  - entrypoint loader: python 143件、process 15件、wasm 0件
  - declared isolation: in_process 95件、process 63件
  - ecosystem.json host_execution=true: 58 Pack
  - *.profile.yaml: 93個
  - *.flow.yaml: 5個

つまり、v3 manifestは広く作られているが、95件のprovider宣言がin_processであり、productionの悪意あるPack前提とは両立していない。Wasmはschema enumにあるだけでruntime実装がない。

2.3 現在のPack実行経路

現在の主な経路は一本ではない。

  A. legacy ecosystem.json -> FunctionRegistry -> CapabilityExecutor/直接dispatch
  B. v3 rumi.pack.v3.json -> capability_binding_registration -> InterfaceRegistry
  C. Pack固有HTTP route -> pack_api_server -> legacy defaultspack route
  D. kernel flow -> kernel handler / python_file_call
  E. Tool broker系Pack ->個別contract client群
  F. connector special-case ingress/egress

v3のloader="process"はmacOS/Linuxでmanaged sandboxへ接続されている。一方loader="python"は承認済みhost execution条件を満たすとimportlibでHost processへloadされる。trusted builtin、core Pack、permissive/legacy経路にもHost実行が残る。

2.4 現在のsandbox

現在のmanaged sandbox foundationは次の構成。

  - macOS: Rumi-owned Lima Ubuntu guest
  - Windows: RumiUbuntu WSL2 distribution
  - Linux: native/Bubblewrap/systemd cgroup
  - Docker provider: optional

重要な制約:

  - macOS/Windowsでは複数sandbox instanceが一つのmanaged guest、同じguest Unix identity、同じkernel namespaceを共有する。
  - separate work directoryはあるが、強いper-Pack filesystem/process isolationを保証していない。
  - Lima/WSL launcherが存在しない環境ではbootstrap未完成。
  - 現行foundationはcoding sandboxやdesktop seatには利用価値があるが、v1.1のunknown native/Python Pack用L4境界ではない。

したがって、現在のsandboxを全部捨てるのではなく、manager、request model、template、audit、workspace overlay、guest protocol、cleanup testを再利用し、provider backendをPackVMへ交換する。

2.5 現在のContractとdispatch

ContractRegistryはsemver、priority、cardinality、chain orderingを解決できる。しかしlive dispatchはInterfaceRegistry/persisted profileを別規則で参照し、実質eligible providerが1件であることを要求する。

不足:

  - resolverが選んだexact providerと実行providerの一致
  - Operation単位のinput/output/error/progress schema検証
  - authoritative RequestEnvelope
  - version/schema digestを含むwire protocol
  - many/fanout/chain/keyedの実行規則
  - Adapter chainの実行
  - deadline/cancelのend-to-end伝播

2.6 現在のProfileとactivation

ResolvedProfile、Profile graph、Capability Profile、Startup Profile、Operating Profileなど複数の概念と正本が併存する。effective_pack_idsが一部activation/graph compile入口へ伝播せず、active identityを解決できないとregistry先頭Packへfallbackする経路もある。

不足:

  - Profile、ProfileLock、ResolvedPlan、ActivationRecordの明確な分離
  - exact digest/schema/policy/isolation/materialization modeのpin
  - atomic pointer swapとcrash recovery
  - Dormant binding
  - materialization journal
  - resource/admission budget

2.7 現在のPolicy、権限、secret

PermissionManager、CapabilityExecutor、AuthorityRequest、Approval、Grant、host permission mapping等は存在する。しかし権限判断が複数レイヤーに分散し、legacy routeやdirect handlerが迂回できる。

Secret Storeは暗号化され、外部APIへ値を出さない意図がある。一方Credential Brokerのresolve operationは、scope確認後にsecret_materialをPack processへ返す。v1.1のbroker-use原則には未到達。

不足:

  - Runtime immutable safety policyを、個別Capability taxonomyを持たない最小の非上書き可能境界にする
  - Profile／管理者ceilingをrestrict-onlyにし、ProfileからHost authorityをmintできなくする
  - Request digest、exact caller/target FunctionPrincipal、ExecutionDomain/boot epoch、activation/policy revision、actual isolationをauthority inputへ固定
  - ProviderAuthorityRecord、ApprovalRecord、GrantRecord、request-bound InvocationLeaseの四分離
  - Host spawn/routing/authenticated channelからFunctionPrincipalを導出し、payload自己申告を信用しない
  - secret valueを返さず、sealed CredentialLeaseを指定Providerがexact Requestにだけ利用する
  - Sandbox authorityとHost authorityを明確に分け、Normal Packからraw Host APIを到達不能にする

2.8 現在のtimeout、cancel、retry

bounded_process_runnerにはcancel_eventとprocess-tree cleanupがある。しかしPack API、global contract dispatch、flow executionへdeadlineが一貫して伝播しない。

  - flowはfuture.result(timeout)後に実行を止めない経路がある。
  - process Contractは固定30秒を使う。
  - Pack API manifest timeoutは保存されても実行に反映されない。
  - flow retryは上限/backoff/idempotencyなしでcontinue相当の箇所がある。
  - non-idempotent external effectのambiguous result管理がない。

2.9 現在のaudit

AuditLoggerと各brokerのaudit eventは存在するが、CapabilityExecutorのauditは例外を握り、writer failure後にbufferをclearする経路がある。write/external_effect/privilegedが監査不能でも成功し得る。

不足:

  - Host生成のauthoritative event
  - append-only sequence/hash chain/signed checkpoint
  - effect前reservationとeffect後commit
  - schema-guided redaction
  - audit unavailable時のeffect class別fail-closed
  - invocation、provider provenance、adapter hop、materializationの統一trace

2.10 現在のinstall/update

PackImporterにはZip Slip、symlink、file count、total size対策がある。PackApplierはstagingからecosystem directoryへcopy/replaceしbackupを作る。署名・artifact integrity部品もある。

不足:

  - immutable content-addressed storeへのcommit

3.3 Protocol v1

  type=invoke
  contract_id
  version_range
  operation_id
  payload
  timeout_ms
  idempotency_key（effect定義に応じて必須）

Packが指定できない項目:

  caller principal
  target provider
  approval/grant/InvocationLease
  profile/policy/authority snapshot revision
  exact schema digest
  actual isolation
  authoritative request/trace ID

Hostが生成するRequestEnvelopeの必須項目:

  request_id、trace_id、correlation_id、causation_id
  Host-authenticated original initiator、current actor
  ordered PackArtifact/FunctionPrincipal/Provider/Adapter delegation chain
  parent request、Workflow run/step/attempt、Approval ceremony provenance
  hopごとにattenuateされたauthority digest
  caller FunctionPrincipal（parent artifact/function implementation/Function/Operation）
  caller ExecutionDomain ID、process/component identity、domain boot epoch
  profile revision、profile authority digest、policy revision、plan digest、activation digest
  target Provider FunctionPrincipal、ProviderAuthority digest、ExecutionDomain ID
  exact contract version、schema digest、operation
  monotonic deadline remaining budget
  opaque request-bound InvocationLease
  validated payload/resource handles

Wire format v1:

  - length-prefixed UTF-8 I-JSON
  - duplicate key、NaN/Infinity、invalid UTF-8、過深nest、oversize拒否
  - integerは原則±(2^53-1)、高精度値はcanonical decimal string
  - JCS RFC 8785でhash/signature canonicalization
  - binary/large objectはResourceHandle
  - cancelはauthenticated control frame
  - streamはstart/data/progress/end/error/cancel/credit、credit-based backpressure必須

3.5 ProviderとAdapter

ProviderDefinitionはmanifest上の宣言、ProviderInstanceは実際のWasm component、Function worker、Host Extension process、PackVM instance、remote endpointである。ResolvedPlanにはexact parent artifact、Function implementation digest、Function/Operation、contract/schema、ProviderAuthority、adapter hops、ExecutionDomain identity/profile、minimum isolationを固定する。

Host Capability ProviderのProviderDefinitionはauthorityを自己付与しない。HostExtensionTrustRecord、Function単位ProviderAuthorityRecord、ExecutionDomainRecordがすべて成立した場合だけHost Provider候補になる。

Adapterは役割であり、automatic structural Adapterとeffectful変換を分ける。

  - structural Adapterはpure、deterministic、bounded、no-network、no-secret、
    no-stateのcapability-free Wasm Componentを原則とする
  - Profileで明示許可/pinされたexact artifactだけ
  - source/target schemaを各hop前後で検証
  - cycle拒否
  - v1最大2 hop
  - lossless優先
  - lossyはProfile opt-in。secret、network、Host authority、state、外部作用を要する
    変換はAdapterではなくProviderまたはWorkflow stepとして扱う
  - effective riskは全hopのcapability、data disclosure、destinationの和集合
  -曖昧なら推測せずerror

3.6 ResourceHandle

Host/PackVM境界へraw host path、secret、open FDを渡さない。Host tableに次を保持し、Packへopaque IDだけ渡す。

  type、owner FunctionPrincipal、allowed target FunctionPrincipal、operations
  ExecutionDomain ID/boot epoch、ResourceHandle namespace
  request binding、Profile/Activation/policy revision、SecurityEpoch
  stable resource identity、expected type、root/provider identity
  inode/device相当、content digest/generation/ETag、version precondition
  range、TTL、use count、max bytes、quota、symlink/reparse/hardlink policy
  revocation state、provenance

file handleはrootをHost側で固定し、Packはrelative pathだけ指定する。利用時は
descriptor/handleベースでstable identityとgenerationを再検証し、writeはatomic
create/replaceまたは明示version preconditionを要求する。

3.7 isolation topology

  Wasm-compatible Pack -> isolated Wasm Component (L3)
  native/Python Pack   -> materialize中だけ専用PackVM (L4)
  remote Provider      -> third-party remote boundary（ordinalなL5ではない）
  GUI contribution     -> Packごとのopaque-origin frontend realm
  TCB                  -> Host in-process (L0)

L1 subprocessはDevelopment Realmだけ。L2 OS sandboxはverified/local Packでplatform conformanceを通した限定用途だけ。unknown native/Pythonのfallbackには使わない。

remoteはexecution containment、operator trust、data locality/region、egress、
filesystem/device reachability、persistence/retention、credential exposure、
auditabilityを独立軸で評価し、payloadを第三者開示として扱う。

3.8 lifecycleとmemory

8/16/32 GiB device classの初期defaultはv1.1の値を採用するが、必ず実測で更新する。

  8 GiB:
    max resident Python=3、background=1、concurrent starts=2、prewarm=0
    profile soft/hard=1024/1536 MiB、runtime hard=2048 MiB
    Python admission/hard=256/384 MiB、idle timeout=30秒

 16 GiB:
    max resident Python=8、background=3、starts=3、prewarm=1
    profile soft/hard=2560/3584 MiB、runtime hard=4096 MiB
    Python admission/hard=320/512 MiB、idle timeout=90秒

 32 GiB:
    max resident Python=16、background=6、starts=4、prewarm=2
    profile soft/hard=5120/7168 MiB、runtime hard=8192 MiB
    Python admission/hard=320/512 MiB、idle timeout=180秒

100 logical Pack/3 busyの標準estimateは追加RAM約1.26 GiB(Linux)、1.48 GiB(macOS)、1.71 GiB(Windows)。100 busyは約31.57/37.86/42.63 GiBであり一般PCでは約束しない。

admission chargeはartifact measured P95、declared minimum、Profile reservation、
runtime floor、backend fixed overheadの最大値にadmitted concurrency setを掛ける。
guest/VMM、shared pageのpolicy charge、Host Extension、queue reservation、state/cache/log、
startup surgeをProfile/Runtime合計へ含め、soft/hard/burst/OOMを分離する。
SuspendedはRAMを保持するため全額chargeし、memory reclaim扱いにしない。

queueはglobal/Profileだけでなくcaller/Pack/bindingごとにbounded quotaと公平性を持つ。
accepted queue itemはresource reservationを所有し、timeout/cancelで解放する。
Host free guardを割る前に新規admissionを拒否する。

idle/pressure eviction state machine:

  Running -> Draining -> BrokerFenced -> AllRequestsQuiesced -> StateFlushed
          -> HandlesRevoked -> Terminated

BrokerFenced後は新しいI/O/effectを開始しない。quiesce失敗はVMM/partition/process
tree killへescalateし、writable overlay、ephemeral key、socket、port forwardを破棄して
materialization journalをStoppedへcommitする。

used VMを別Packへ再割当てしない。Pack-specific RAM snapshotを作らない。prewarmはPackコード/secret/stateを一度も入れていないclean generic VMだけ。

  - one-shotの並列消費はatomic CASで一つだけ成功する。
  - unknown/unverifiable scope semanticsをfail-openせずone-shot/opaque trustへ落とす。
  - arbitrary executable policy/subset/approval pluginをKernelへloadしない。
  - sandbox内部計算には不要なApprovalを出さない。
  - 新しいvendor Pack追加にPolicy Kernelのvendor固有permission code追加を必要としない。
  - 未承認Function、別digest、別callerが承認済みCapability FunctionのGrantを再利用できない。

  - diagnostics storeとsecurity audit storeを分離
  - bounded emergency journal

failure policy:

  pure/read: emergency journalが書ける場合のみ継続
  write/external_effect/privileged: authoritative reservation不可ならdeny

完了条件:

  - disk full、permission error、writer crashをfault injectionし、外部作用がfail-closedになる。
  - Packがauthoritative audit eventを偽造できない。

Phase 11: FunctionからOperationへのPack移植

Phase 13: Workflow PackとScheduler Pack

Workflow models:

  Definition: draft -> published -> archived
  Run: queued -> running <-> paused -> succeeded/failed/cancelled/needs_reconciliation
  StepAttempt: pending -> dispatching -> running/waiting_approval
               -> succeeded/failed/cancelled/timed_out/ambiguous_effect

実装:

  - Workflow Definition/Run/StepAttempt/checkpoint store
  - published revisionとActivationRecordをRun開始時にpin
  - Workflow全体のambient Grantは禁止し、各Step向けatomic Grantへ展開
  - Grantをworkflow ID/published revision digest/step/attempt/call chainへbind
  - stepはContract Requestだけ
  - restricted CEL subset、I/Oなし
  - parallel child attemptの実並列とbounded concurrency
  - retry count/backoff/idempotency/attempt history
  - approval待ちpauseとcontinuation。checkpointへRequest/effect/call chain/idempotencyを保存
  - checkpointへInvocationLease/raw credential/unbounded Host handleを保存しない
  - resume/retry/parallel/sub-workflowの各StepAttemptでGrantとsnapshotを再評価
  - cancelのRequest/Providerへの伝播
  - crash recoveryとambiguous effect reconciliation
  - Host TCBの最小Trigger/Wake Kernelがdurable registration、OS wake、monotonic
    due time、occurrence claim、bounded at-least-once delivery、quotaを担当
  - wake前とdelivery前にSecurityEpoch/revocationを確認しtrigger-specific one-shot Leaseを発行
  - SchedulerはTrigger Contractで接続する別Packで、calendar/recurrence/timezone/retry意味論を担当
  - occurrence ID + workflow revisionでduplicate start防止
  - editor paletteをactive Contract Catalogから生成
  - ETag/revision/optimistic locking/compile preview

三系統のschedulerは一つのScheduler Packへ統合する。ただしDormant Packを起動する
domain-independent Trigger/Wake KernelはRuntime TCBへ残し、Scheduler Pack codeを
wake admission判断中に実行しない。

10. 完成の定義
--------------

この再設計は、画面上でPackが動いた時点では完成ではない。次をすべて満たした時点をv1完成とする。

  - public Pack APIがContract Operation Requestだけ。
  - ecosystem PackのHost import/cross-Pack importがない。
  - FunctionRegistry、legacy route、python_file_call、host fallbackがない。
  - install/resolveでPack codeを実行しない。
  - Profileがexact artifact/provider/schema/isolationをdeterministicにpinする。
  - ProfileがBase Packとcompatible Shell Providerを別bindingとしてpinする。
  - defaults-basepackをTauri/CLI Shellで共有し、backend state/routingを複製しない。
  - CLI ShellではGUI artifact、Tauri Shellではambient TTY contributionを起動しない。
  - Production launchからcargo tauri dev/npm run dev/arbitrary command stringへ到達できない。
  - logical activationとmaterializationが分離される。
  - unknown native/Python Packはcertified L4だけで起動する。
  - internal sandbox操作は不要な承認なしで動き、境界越えだけGrantされる。
  - Runtime Coreがvendor/Capability固有permission taxonomyを中央列挙しない。
  - Host Extension SDKから未知CapabilityをFunction/Operationとして追加できる。
  - secret valueをPackへ返さない。
  - ApprovalRecord、ProviderAuthorityRecord、GrantRecord、InvocationLeaseが混同されない。
  - Pack/publisher/Profile/Distribution wildcard Grantが存在しない。
  - ProviderAuthority/Grantはexact caller/target FunctionPrincipal/Operation/domainへbindされる。
  - Function identityはHost spawn/routing/channelから導出される。
  - unknown/unverifiable semanticsはfail closedまたはone-shot/opaque trustへdowngradeされる。
  - lease_onlyとos_entitlementが区別され、後者のblast radiusが表示される。
  - same-Pack未承認Functionが承認済みFunctionのauthority stateを共有しない。
  - Profileはauthorityをmint、拡張、exportできない。
  - Production Normal Packのraw networkが0。
  - external effectはPolicy、Grant、request-bound Lease、audit reservationを必ず通る。
  - timeout/cancel/eviction/update後にHost所有local実行物と権限が残らない。
  - remote/accepted external effectはambiguous_effectとreconciliationで扱い、停止を偽装しない。
  - GUI security chromeをPackが被覆・interceptできず、trusted-attention cueを偽造できない。
  - Workflowがcheckpoint、approval pause、cancel、retry、reconciliationを持つ。
  - 100 logical Packが100 VMを意味しない。
  - macOS/Windows/Linuxは、それぞれconformance合格したbackendだけを対応表示する。
  - Docker/Homebrew/manual shellなしでライトユーザーがsetupできる。
  - malicious fixture、fault injection、resource benchmarkがrelease gateとして常時passする。


11. 現実的な難易度評価
----------------------

これは大規模かつ根本的なrewriteである。特に難しいのはContract schemaではなく、次の4点。

  1. 三OSのproduction-grade PackVM supervisorと配布
  2. Policy/Grant/Audit/Requestを迂回不能な唯一経路にすること
  3. logical Profileとphysical VM lifecycleのatomic recovery
  4. 既存の多数のPack、GUI、Workflow、Connectorを旧direct callから移植すること

一方、既存データ互換を必須にせず、プロジェクトが未完成の段階で全面移行できるため、二重互換を長期間維持するより成功確率は高い。最も重要なのは、全機能を同時に直すことではなく、Notificationの小さなvertical sliceで「artifact -> profile -> request -> policy -> sandbox -> effect -> audit」の完全な一本線を先に完成させ、その線以外の実行経路を増やさないことである。
