# LauncherでFlowを作る

LauncherのFlowは、Profileで利用を許可した処理をノードとして並べる画面です。
ノードをつなぐ操作と、処理の実行・権限の承認は別です。編集しただけでAPIへ送信したり、Packのネットワーク権限を増やしたりしません。

## 最初の音声Flow

1. Launcherで対象のProfileを確認します。別Profileを閲覧中の場合は読み取り専用です。実行対象の切り替えは通常のProfile操作で行います
2. Flowの「接続・モデルをこの画面で登録」を開き、必要なAPI接続とモデルを登録します。Settingsの「接続・モデル」と同じ、現在のProfileの登録先を使います
3. 空のFlowで「音声会話のFlowを作る」を選びます。音声認識、テキスト生成、読み上げの3つの契約が実際のProfileにない場合は作成できず、必要な操作を表示します
4. 各ノードを選び、それぞれ対応する登録済みモデルを指定します。読み上げにはプロバイダーに対応する声のIDも指定します。モデルが登録済みであることと、その処理に対応していることは別です
5. FlowのIDを入力して「Create draft」で保存し、「Validate」で確認します。「Publish selected draft」は保存した内容を実行用の変更できない版にします。公開は権限承認ではありません
6. 「Flowを実行」で音声ファイルを選び、実行します。必要な承認はHostの承認画面で内容を確認します。承認待ちの処理は、画面を閉じてしまった場合は「承認画面を開く」で開き直せます。表示するだけでは承認・再実行されません。承認後に「続行」で進めます
7. 各段階の文字結果と、最後の音声結果を確認します。音声は自動再生しません

現在の音声入力は1MiB以下のファイルです。大きな音声をURLやローカルパスへ置き換えて制限を回避する機能はありません。
音声のネットワーク処理は、明示的に音声用途を承認したOpenAI互換の登録接続を使用します。既存のテキスト専用接続が自動的に音声用途へ拡張されることはありません。
APIキーはFlowの定義、ノード、実行入力に書かず、接続の登録画面だけで扱ってください。

## ノード編集

- 四角い端子は実行順序、丸い端子はデータです。出力を選んでから、次のノードの対応する入力を選びます
- 型が合わない端子、循環する接続、同じノードへの接続は選べません。最終的な入力検証はHost側でも実施します
- ノードの見出しをドラッグして移動します。「全体を見る」で表示範囲に合わせ、「整列」で初期配置に戻せます
- ノードを選ぶと設定欄が開きます。設定欄は閉じられます。表示名の変更では内部IDや処理の接続は変わりません
- 配置は同じブラウザーのセッション内でProfileとFlow IDごとに記憶します。配置は実行権限でも、別端末へ同期されるデータでもありません
- Undo/Redoは編集中の定義変更を戻します。実行済みのAPI呼び出しや外部への変更を取り消す機能ではありません
- 詳細な定義はSource JSONから編集できます。入力はJSONですが、式の評価、任意のJavaScript、任意のファイル読込みは行いません

## 実行結果が不明なとき

新しい実行を繰り返し作らず、「状態を再取得」で元の実行を確認してください。
停止は、すでに完了した外部の変更や発生したAPI料金を巻き戻しません。
実行の結果と停止が競合して断定できない場合は、要確認の状態を保持します。成功や安全な再実行と決めつけません。
大きな出力は画面のプレビューだけを省略することがあります。

## 開発者がノードを追加するには

1. Packが提供するContractの入力・出力JSON Schemaを明示します。モデル選択フィールドには、文字列型と表示ヒント `x-tobkiri-selector: model-profile` を宣言します
2. 実装とContractを通常のPack生成・検証手順で登録します。画面用の型情報は正式なスキーマから縮小した表示用データであり、元のスキーマや権限の代わりにはなりません
3. ProfileでWorkflowからその処理への正確な呼出し先を宣言し、通常のProfile変更確認を行います。Packを入れただけで、Profileの全操作がWorkflowから使えるわけではありません
4. 他ノードの入力には `${steps.<step_id>.output.<field>}` を使えます。参照元を `depends_on` に宣言し、同じ実行で成功が確定した出力だけを参照します。開始時の入力は `${inputs.<field>}` です
5. 単独Packテストに加え、実際のProfileからパレットへスキーマが届くこと、保存・公開・承認・Broker実行・停止・再開まで確認します。ブラウザーのモック表示だけでは実行経路の検証になりません

大きな音声やファイル、別プロセスのUI拡張、Profile間の資格情報共有は、それぞれ別の権限とデータ所有の設計が必要です。Flowの表示だけで暗黙に許可しないでください。
